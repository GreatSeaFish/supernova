### 🛠️ 团队协同标准工作流
我们采用 **特性分支（Feature Branch）** 模式，配合以下核心机制：
1. **统一的基线（Baseline）控制**：`main` 分支永远只存放当前最稳定、胜率最高的版本。
2. **变合并（Merge）主分支测试**：任何人在提交测试前，必须将最新的主分支代码拉取（Pull）或合并到自己的分支，**在确保没有代码冲突和策略冲突的前提下，再进行 100 场测试**。

假设小组成员 A 想要优化“球员拦截（Intercept）”策略。
#### 第一步：从最新的主分支切出特性分支
开发前，必须保证本地的 `main` 分支是最新的。
创建新分支`feature-intercept-optimize`
#### 第二步：本地修改与策略开发
在 `feature-intercept-optimize` 分支上修改代码。
#### 第三步：检查并同步最新的主分支（测前对齐）
在准备启动 100 场大规模胜率测试前，**必须检查在自己写代码的这段时间里，有没有队友已经合并了新的代码到 `main` 分支**。
- **如果没有新的合并**：跳过此步
- **如果已经有了新的合并**：
拉取远程最新的主分支，将最新的 main 分支合并到你的特性分支
```
git checkout main
git pull origin main  # 拉取远程最新的主分支
git checkout feature-intercept-optimize
git merge main        # 将最新的 main 分支合并到你的特性分支
```
- **如果有冲突**：就地解决代码冲突，并重新检查逻辑。
- **如果没有冲突（或者解决完冲突）**：此时，你的特性分支就变成了 **“当前最新的主分支代码 + 你的修改”** 的完全体。**只有在这个状态下进行的测试，结果才是100%准确的。**
#### 第四步：启动 100 场胜率测试（自动化评估）
使用自动化脚本跑 100 场比赛。
- **对手选择**：选择一个**固定的、有代表性的强敌**（例如原版的 HeliosBase 或是去年世界赛前 8 的某支开源队伍）
#### 第五步：在群里发测试截图
在 GitHub 上合并分支前，请在群里通知一声
#### 第六步：合并
